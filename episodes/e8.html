مفهوم DC Cloning (مجازی‌سازی ایمن)

در گذشته، گرفتن Clone (کپی) یا Snapshot از یک سرور Domain Controller در محیط‌های مجازی (مثل VMware یا Hyper-V) یک فاجعه بود و باعث خطای وحشتناک USN Rollback می‌شد که کل دیتابیس را به هم می‌ریخت.

قابلیت DC Cloning (از سرور 2012 به بعد)

مایکروسافت با معرفی ویژگی Virtualization Safeguards این مشکل را حل کرد. حالا می‌توانیم از یک DC در محیط مجازی با امنیت کامل Clone بگیریم تا به سرعت یک Additional DC جدید بسازیم (مخصوصاً برای مواقع بحرانی یا دیتاسنترهای بزرگ).

پیش‌نیازهای قطعی Cloning:
  • سرور PDC Emulator باید آنلاین و در دسترس باشد.
  • DC ای که می‌خواهیم از آن کلون بگیریم باید عضو گروه Cloneable Domain Controllers در اکتیو دایرکتوری باشد.
  • باید فایل پیکربندی به نام DCCloneConfigFile.xml (حاوی تنظیمات IP و نام سرور جدید) ساخته و در پوشه NTDS قرار گیرد.

معماری HA: تفاوت عمیق NLB و Failover Cluster

مفهوم HA (High Availability) یا دسترسی‌پذیری بالا یعنی حذف نقطه‌ی تکی شکست (Single Point of Failure). اگر یک سرور خاموش شد، سرور دیگر بدون وقفه کار را ادامه دهد. مایکروسافت برای این کار دو تکنولوژی کاملاً متفاوت ارائه داده است:

Network Load Balancing (NLB)

طراحی شده برای سرویس‌های Stateless (بدون وضعیت) مثل وب‌سرورها (IIS) یا پروکسی‌ها. هیچ دیتای مشترکی بین سرورها وجود ندارد.

  • Active-Active: همه سرورها همزمان با یک IP مجازی (VIP) روشن هستند و بار ترافیک بین آن‌ها تقسیم می‌شود.
  • فقط شبکه را می‌فهمد: NLB فقط آی‌پی و پورت شبکه را چک می‌کند. اگر سرویسِ IIS (نرم‌افزار) روی سرور ۱ متوقف شود اما سرور پینگ داشته باشد، NLB متوجه نمی‌شود و ترافیک را می‌فرستد!
  • توسط پالس‌های Heartbeat خرابی سخت‌افزاری سرورها را متوجه شده و ترافیک را قطع می‌کند.

Failover Cluster

طراحی شده برای سرویس‌های Stateful (وضعیت‌دار) مانند دیتابیس‌ها (SQL Server) یا فایل‌سرورها. این سیستم به شدت پیچیده و گران‌قیمت است.

  • Active-Passive: معمولاً یک سرور کار می‌کند و سرور دوم در حالت آماده‌باش (Standby) است.
  • سرویس و استوریج را می‌فهمد: به عمق سیستم‌عامل نفوذ می‌کند. اگر سرویس SQL متوقف شود، فوراً متوجه شده و دیتابیس را روی سرور دوم بالا می‌آورد.
  • نیاز قطعی به Shared Storage (استوریج مشترک) مانند SAN دارد.

Application Load Balancing و امنیت (C&C)

Application Load Balancing (لایه ۷)

برخلاف NLB مایکروسافت که در لایه ۴ (شبکه) کار می‌کند، لود بالانسرهای سخت‌افزاری/نرم‌افزاری پیشرفته (مثل F5 Big-IP یا HAProxy) در لایه ۷ (Application) کار می‌کنند.

این یعنی ترافیک وب (HTTP/HTTPS) را می‌خوانند، کوکی‌ها را می‌فهمند و می‌توانند بر اساس وزن (Weight) ترافیک را تقسیم کنند (مثلا سرور A چون رم بیشتری دارد، ۳ برابر سرور B ترافیک بگیرد). آن‌ها حتی می‌فهمند کاربر کدام URL خاص را درخواست داده و ترافیک را به سرور مخصوص آن هدایت می‌کنند.

C&C Server (Command and Control) چیست؟

در دنیای امنیت شبکه، سرورِ C&C یا C2، سروری است که توسط هکرها کنترل می‌شود تا به بدافزارها و سیستم‌های آلوده‌شده (Botnets) در شبکه‌ی ما دستور بدهد. سیستم‌های آلوده مدام برای دریافت دستور به این سرورها متصل می‌شوند (Beaconing).

ارتباط با Load Balancer: لود بالانسرهای لایه ۷ و WAFها (Web Application Firewalls) ترافیک خروجی و ورودی را مانیتور می‌کنند. اگر یک سیستم داخلی سعی کند با یک IP مخرب (C&C Server) ارتباط بگیرد، لود بالانسر به دلیل درک ترافیک لایه اپلیکیشن، این رفتار مخرب را شناسایی و مسدود می‌کند.

معماری کارت‌های شبکه در NLB

برای راه‌اندازی NLB، تمام سرورهایی که می‌خواهند در کلاستر شرکت کنند باید فیچر NLB را نصب داشته باشند. اما مهم‌ترین چالش معماری NLB، تعداد کارت‌های شبکه (NIC) روی سرورهاست:

Single NIC (یک کارت شبکه)

در این حالت، سرورها فقط یک کارت شبکه دارند. ترافیک کاربران (VIP) و ترافیک Heartbeat (ارتباط خود سرورها با هم) هر دو از یک کابل رد می‌شوند.

چالش: در مود Unicast با یک کارت شبکه، سرورها نمی‌توانند به راحتی با هم صحبت کنند، زیرا MAC کارت شبکه‌شان تغییر می‌کند!

Dual NIC (دو کارت شبکه) - Best Practice

سرورها دو کارت شبکه دارند. یک کارت شبکه فقط و فقط به ترافیک کلاینت‌ها (کلاستر / VIP) اختصاص می‌یابد و دومی یک کارت شبکه اختصاصی است که صرفاً برای رد و بدل کردن پالس‌های Heartbeat و رپلیکیت دیتای مدیریتی بین خود سرورها استفاده می‌شود. این روش بالاترین پایداری را دارد.

کانفیگ ۰ تا ۱۰۰، Modeها و Port Rules

فرایند راه‌اندازی (Step-by-Step)

  1. نصب فیچر: نصب Network Load Balancing روی تمام سرورها.
  2. کنسول مدیریت: باز کردن NLB Manager روی سرور اول، کلیک راست و New Cluster.
  3. افزودن Host: وارد کردن IP سرور اول و انتخاب کارت شبکه‌ای که قرار است ترافیک را بگیرد.
  4. تعیین VIP: اختصاص دادن Virtual IP (VIP)؛ این همان IP است که در DNS برای سایت ثبت می‌شود و کاربران آن را می‌بینند.
  5. تعیین Mode: انتخاب یکی از حالت‌های Unicast / Multicast.
  6. افزودن نودهای بعدی: کلیک راست روی کلاستر ساخته شده و زدن Add Host to Cluster برای سرورهای دوم و سوم.

حالت‌های عملیاتی (Cluster Operation Modes)

Unicast

مک آدرسِ فیزیکی کارت شبکه سرور را حذف کرده و مک آدرس مجازی کلاستر را جایگزین می‌کند. چون همه سرورها یک MAC یکسان دارند، باعث Switch Flooding می‌شود تا سوئیچ ترافیک را به همه پورت‌ها بفرستد.

Multicast

مک آدرس اصلی سرور را نگه می‌دارد و یک مک آدرس Multicast به آن اضافه می‌کند. از Switch Flooding جلوگیری می‌کند اما نیاز دارد ادمین شبکه روی روتر تنظیمات ARP استاتیک بنویسد.

IGMP Multicast

بهترین و هوشمندانه‌ترین حالت! با استفاده از پروتکل IGMP به سوئیچ (اگر پشتیبانی کند) دقیقاً می‌گوید کدام پورت‌ها عضو کلاستر هستند تا ترافیک فقط به همان پورت‌ها برود.

قوانین پورت (Port Rules) و مفهوم Priority

در تب Port Rules تعیین می‌کنیم که کلاستر روی چه پورتی ترافیک را بالانس کند (مثلاً فقط ترافیک TCP پورت 443 بین سرورها تقسیم شود).

معمای Priority در پورت‌های متفرقه:

وقتی هاست‌ها را اضافه می‌کنیم، به هر سرور یک شناسه Host ID (Priority) از ۱ تا ۳۲ داده می‌شود. کاربرد این عدد چیست؟

فرض کنید قانون (Port Rule) فقط برای پورت ۴۴۳ نوشته شده است. حالا اگر یک کاربر به IP کلاستر در پورت ۸۰ یا ۲۱ وصل شود چه می‌شود؟
در اینجا ترافیک بالانس نمی‌شود! بلکه سروری که Priority بالاتری دارد (یعنی عدد آن کمتر است، مثلاً ۱) به عنوان Default Host شناخته شده و تمام ترافیک‌های متفرقه (که در Rule نیستند) مستقیماً و فقط به آن سرور ارسال می‌شوند.
